Proposal Resolves open question 3 Issue #102 · Phase 3

Broker, Not Peer

A2A assumes every agent is a server with a URL. MemPalace is a mailbox. Reconciling those is not a compromise — the A2A spec already has first-class vocabulary for it, and using that vocabulary is what lets an agent on a laptop participate without ever opening a port.

The question this answers

Why the Agent Card was a shell

Stage 5 shipped the mempalace-a2a mapping crate, but left one thing unbuildable. The A2A AgentCard requires supported_interfaces: a non-empty, ordered list where every entry carries a resolvable absolute HTTPS URL. We had no endpoint, so there was nothing truthful to put in it. The card was recorded as not spec-compliant for a live transport — deviation 25.

The instinct was to treat that as a missing feature: give the adapter an HTTP surface and fill the field in. That instinct is wrong, and the reason is worth stating precisely, because it changes what gets built.

The reframing

The disagreement is about who holds the socket

A2A's default topology is peer-to-peer. Each agent is a server, has an address, and gets dialled. Discovery means fetching a card, reading a URL, and posting to it.

MemPalace is a broker. There are tasks, an inbox, and opaque cursors, and agents pull the work addressed to them. An agent behind a mailbox needs no inbound port, no TLS certificate, and no public address — which is exactly what makes an agent running on a laptop a first-class participant rather than a second-class one.

The load-bearing find

A2A already has a word for this

This is not a departure from the protocol. AgentInterface carries an optional tenant field, and the v1.0.1 proto defines it as exactly the broker case:

An opaque string used for routing requests to a specific agent or tenant when multiple agents are served behind a single A2A endpoint. When set, clients MUST include this value in the tenant field of all request messages sent to this interface.

a2aproject/A2A · specification/a2a.proto · v1.0.1

The protocol deliberately leaves the format undefined — the server interprets it. That is the whole mechanism we need, already specified, already required of conforming clients.

A2A conceptMaps to
supported_interfacesOne entry: the palace's own URL. There was only ever one endpoint to advertise.
tenantOne registered agent. Many agents, one address.
SUBMITTEDPending — already means “accepted, nobody working it yet”. An offline agent is not an error condition.
PollingOpaque cursors, already the stated compatibility baseline in issue #102.

Resolving deviation 25 therefore costs nothing new. It is not an endpoint per agent; it is the recognition that the palace was the addressable thing all along.

The honest cost

Two capabilities we give up, and say so

AgentCapabilities.streaming and push_notifications are declarations about the agent. An agent that pulls from a mailbox cannot stream to a caller. The palace could stream on its behalf — but then it is asserting a property the registered agent does not have.

Declare both false and mean it

Synthesising these at the broker is the same silent-coercion failure the crate already refuses everywhere else: a claim that reads as true, with the fact that it was manufactured left nowhere in the record. The crate returns coercion provenance rather than a bare From impl for precisely this reason. The broker should not quietly do at the capability layer what the state mapping is forbidden from doing at the value layer.

The distinction to hold

“A2A adapter” is two things

Conflating these is the trap. They differ in who serves, and therefore in auth model, code path, and failure mode.

DirectionWho servesShape
Inbound
external client → palace → agent		 Palace Broker. Agent pulls. Needs tenant routing and per-agent authorization.
Outbound
palace agent → external agent		 They do An HTTP client, structurally like mempalace-remote. Here the remote genuinely has a URL and we dial it.

The mapping crate already serves both directions — it is pure translation and does not care who holds the socket. The exposure work does not: these are two separate pieces of build, and only inbound depends on answering this question.

Where cards live

wing_registry

Registration cards cannot live in wing_agents. That wing carries the unconditional diary hard-override and never federates under any configuration, which would make every card undiscoverable — defeating the purpose of registering it.

A sibling wing is safe. Every diary-override comparison in the codebase is an exact == against "wing_agents"; there is no prefix or substring matching on the wing anywhere, so a distinct name is genuinely clear of it.

The override has a second dimension

It is not only the wing. Several sites read wing == SHARED_AGENT_DIARY_WING || room == DIARY_ROOM. A card filed into a room named diary is blocked from federating regardless of which wing it sits in. “Put it in a different wing” is only half the rule.

This wing inverts the default posture

Everywhere else in MemPalace, memory stays local unless deliberately routed out. wing_registry federates by definition — that is its entire purpose. It therefore needs an explicit, stated rule about what may be filed there.

The failure mode is mundane and likely: someone reasons “agent things go in the agents wing”, picks the wrong one, and has it replicate silently. The name wing_registry was chosen over wing_agent_public for exactly this reason — two wings with opposite egress semantics should not differ by six characters.

Not yet built

What this needs to become real

Nothing here is implemented. This is the design as agreed in conversation, written down so it is reviewable rather than remembered.

  • wing_registry as a well-known constant alongside SHARED_AGENT_DIARY_WING and UNSCOPED_WING — a string convention is not enough if discovery depends on it.
  • Load-time validation, and a stated content rule for what may be filed into a wing that federates by definition.
  • Agent Card generation from a registry entry: palace URL, per-agent tenant, streaming and push_notifications both false.
  • Inbound routing: resolve tenant to a registered agent, then to its task queue and authorization scope.
  • Update deviation 25 — the Agent Card limitation is resolved by this design, not outstanding.
  • Docs per CLAUDE.md: Config-Schema.md, Federation.md, and open question 3 in Coordination-Phase-3-Design.md.

Unverified assumption worth checking first

The protocol claims here come from the v1.0.1 proto's field definitions and comments. That is solid on the wire contract and stated intent, but it does not establish how major A2A implementations behave in practice — in particular, whether clients actually honour tenant routing and interface preference order. Confirm against a real implementation before building inbound; it is the one assumption here that could quietly not hold.

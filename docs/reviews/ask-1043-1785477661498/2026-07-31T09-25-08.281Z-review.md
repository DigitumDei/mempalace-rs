## Executive Summary

The branch adds projected-ID duplicate checks and a configuration option to disable automatic maintenance while retaining manual maintenance. The primary alleged blocker is invalid because the base revision already used include_all_views=true, so this branch does not introduce the claimed cross-view behavior change. The remaining concerns are non-blocking coverage, observability, and timing-test robustness gaps.

- Manual-only maintenance mode is not distinguishable in status or info responses: With maintenance enabled but background_enabled=false, the server reports Idle even though no scheduler is active, and the info response does not expose background enablement.

# Blocking Issues

**1. `existing_ids` silently changes `include_all_views` from `false` to `true` — untested behavioral change in duplicate detection**

`crates/mempalace-storage/src/lance.rs:179-183`: The old code on `main` uses `DrawerFilter { ids: ids.to_vec(), ..DrawerFilter::default() }`. `DrawerFilter` derives `Default`, so `include_all_views` is `false`. The new code explicitly sets `include_all_views: true`. With `include_all_views: false` and `view: None` (the default), `compile_filter` at line 827 adds `ingest_mode != 'projects-branch'` to the SQL. With `include_all_views: true`, the function returns early at line 820-821, skipping that filter. This means the old `existing_ids` only checked for duplicates in non-branch rows; the new one checks across all rows. This is a semantic change in duplicate detection. While the new behavior is arguably correct (IDs should be unique across all views), it is completely undocumented, unjustified, and untested. This could reject writes that were previously accepted, or cause `Overwrite` to delete rows in a different view.

**2. No test for the `existing_ids` column-projection optimization**

The `existing_ids` method was rewritten to use `Select::Columns(vec!["id".to_owned()])` instead of `list_drawers()` to avoid loading full records and embeddings. There is no direct test that verifies the projection works correctly. The existing tests exercise `existing_ids` indirectly through `put_drawers` `DuplicateStrategy`, but these tests would also pass with the old implementation. There is no test that verifies the projection specifically avoids loading embeddings, nor that `ids_from_batches` correctly handles the projected batch.

# Non-Blocking Issues

**3. `manual_maintenance_creates_no_scheduler` uses a sleep-based assertion**

`crates/mempalace-server/src/lib.rs:3700`: The test sleeps 500ms and asserts no status was recorded. While technically correct (since `background_enabled: false` prevents any maintenance from running), this pattern is fragile. The existing `maintenance_startup_check_records_status` test at line 3670 uses a polling loop up to 2.5s, which is more robust. The new test should use the same pattern.

**4. `enabled` field doc change is misleading**

`docs/Config-Schema.md:108`: The doc for `enabled` was changed from "whether the maintenance subsystem runs automatically" to "whether the maintenance subsystem is available." The new wording is misleading because when `enabled=false`, `run_maintenance` at `engine.rs:482` returns early. The CLI `maintain` command also passes `enabled` from config, so manual maintenance is also disabled. The `enabled` field is the master kill switch, not an availability toggle. `background_enabled` is what controls automatic vs. manual scheduling.

**5. `ids_from_batches` has no unit test**

The helper function at `lance.rs:1131` is new and has no dedicated unit test. It is only exercised indirectly through `existing_ids`, which itself has no direct test.

# Missing Tests

- Unit test for `existing_ids` verifying the column-projection returns correct IDs without loading embeddings.
- Unit test for `ids_from_batches` verifying correct extraction of string IDs from RecordBatches.
- Integration test verifying that `background_enabled: false` + `enabled: true` still allows `mempalace-cli maintain` to complete (proving manual maintenance works when automatic is disabled).
- Config test verifying `background_enabled` defaults to `true` when omitted from JSON (the `defaults` test at line 1205 already covers this for the `defaults()` constructor, but the empty-JSON path in `from_json` is not explicitly tested for this field).

# Strong Concerns

**The `include_all_views` behavioral change in `existing_ids` is a silent, untested change that could affect duplicate detection in production.** If the old behavior was intentional (e.g., branch-view drawers were allowed to have IDs that conflict with canonical drawers), this change would break that assumption. The commit message says "perf(storage): add manual maintenance mode" — nothing about changing duplicate detection semantics. This is a correctness change disguised as a performance optimization.

**The `enabled` vs. `background_enabled` semantics are unclear from the docs.** The doc says `enabled` means "available" and `background_enabled` means "automatic." But `run_maintenance` checks `enabled` first and returns `Partial` (not `Disabled`) when it's `false`. The server's `maintenance_status` is set to `Disabled` when `enabled=false` but `Idle` when `enabled=true` + `background_enabled=false`. These states are inconsistent — the subsystem is described as "available" but reports `Disabled` when `enabled=false`.

# Confidence

Medium. The `existing_ids` projection optimization is sound and the `background_enabled` config plumbing is correct. But the `include_all_views` change and the lack of tests for the new code paths are concerning. The sleep-based test is a code smell but not a defect.

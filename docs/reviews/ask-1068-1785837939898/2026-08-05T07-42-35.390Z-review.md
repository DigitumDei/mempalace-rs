## Executive Summary

The branch strengthens source discovery and secret exclusion across Git-index and filesystem workflows, including ignore-file handling and denylist reporting. Reviewers consistently found that unlimited canonical re-mining does not remove stable-prefix rows for files now excluded by the new policy, allowing previously ingested secrets, untracked files, or symlinks to remain searchable. Because this undermines the security objective during upgrades, the branch requires revision before it is ready for PR.

## Blocking Issues

- Canonical re-mining leaves stale stable source rows (mempalace-ingest/src/lib.rs): Canonical cleanup removes only legacy-prefix rows and does not enumerate the current stable project-source prefix to delete files absent from the newly eligible source set. Previously mined secrets, untracked files, or symlinks can therefore remain stored and searchable after re-mining.

## Non-Blocking Issues

- Secret denylist patterns are broader than necessary: The `.env` prefix and unanchored `kubeconfig` matching can exclude unrelated filenames. This is a safety-first tradeoff, but the boundaries should be documented or tightened.
- Secret skip summary semantics are not explicit: Secret paths are captured before branch-delta filtering and limit application, so summaries may include unchanged or out-of-scope paths.
- Filesystem skip ordering is nondeterministic: Secret skip records follow filesystem traversal order rather than the sorted source order, which can make rendered summaries vary between runs.

## Missing Tests

- Seed stable canonical rows for a previously mined secret, untracked file, and tracked symlink, then verify an unlimited canonical re-mine removes them.
- Verify stale-row cleanup is isolated to the current project or repository identity.
- Exercise secret-path summary rendering through canonical Git-index mining.
- Add boundary tests for intentionally broad secret-denylist patterns and summary behavior outside branch deltas or --limit.

## Disputed Issues

- Whether the custom glob matcher has meaningful Git-wildmatch incompatibilities beyond the unverified character-class edge case.
- Whether global-excludes loading for non-Git walks and unpinned CLI tests should be treated as defects or documented design and test-hygiene concerns.
- Whether filesystem and Git-index skip counters have problematic semantic inconsistency.
- Whether the hardcoded worktree .gitignore loading is an API-clarity issue or a functional defect.

## Outstanding Concerns

- The new global core.excludesFile behavior can surprise users by excluding files from non-Git project walks, although it is documented and may be intentional.
- The denylist's safety-first breadth lacks an explicit recovery or override path for false positives.

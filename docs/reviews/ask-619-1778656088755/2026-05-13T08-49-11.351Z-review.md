## Executive Summary

This branch transitions diary storage from per-agent siloed storage to shared operational memory across wings: project-scoped entries route to named project wings, agent-scoped entries go to a shared `wing_agents` wing, and reads default to a 24-hour cross-wing scan with optional filters for since, wing, agent_name, and topic. The core routing logic, attribution via `added_by`, and in-memory filtering are internally consistent, and the test suite covers the main happy paths for writes, reads, and legacy migration with no data-loss or correctness bugs identified. However, the wake-up diary is silently hard-capped at 24 hours with no override or response-level signal — a behavioral regression from the old unlimited `diary_read_all_agents` — and key error-condition paths (project-scope write without a wing, invalid `since` format, old entries excluded from wake-up) are untested. The verdict is `revise` to address missing test coverage and either expose a `diary_since` parameter on wake-up or at minimum surface the active time window in the response.

## Non-Blocking Issues

- Wake-up diary payload emits redundant `"agent": null` alongside `"current_agent"` (src/lib.rs): `DiaryReadFilters::default_with_last_n` sets `agent_name: None`, which serialises as `"agent": null` in the payload. `diary_read_all_payload` then injects `"current_agent"` on top, producing two keys with different semantics in the same response object.
- `scope == "agent"` with an explicit `wing` is silently discarded (src/lib.rs): The schema documents that `wing` is ignored for agent-scoped entries, but the runtime emits no warning or error. Callers who pass both get silent discard; this is a UX hazard even if not an undocumented behavior.
- `scope` is not persisted to drawer records (src/lib.rs): `scope` appears in `ChangeEvent.details_json` but not in the stored `DrawerRecord`. Entries from project wings and `wing_agents` look identical when read back; context is implicit via the `wing` field only.
- `last_n` is parsed outside `DiaryReadFilters::from_arguments` (src/lib.rs): `tool_diary_read` extracts `last_n` before calling `from_arguments`, which then accepts it as a pre-parsed parameter rather than reading it from the arguments map itself. Splits argument-parsing responsibility in a surprising way.

## Missing Tests

- `scope == "project"` without a `wing` field should return `InvalidParams` — the enforcement path in `diary_write_wing_name` is real but entirely untested.
- Cross-wing unfiltered read: no test writes one entry to a named project wing and one to `wing_agents` then issues `diary_read` with no filters and asserts both entries are returned.
- Invalid `since` format: `parse_since_timestamp` returns a user-facing error string but no test exercises this error path.
- Wake-up with entries older than 24 hours: no test inserts a `DrawerRecord` with a historical `filed_at` and asserts it is excluded from the wake-up payload, leaving the 24-hour truncation behavior unverified.

## Disputed Issues

- None

## Outstanding Concerns

- Wake-up diary is hard-capped at 24 hours with no override and no response-level signal. `diary_read_all_payload` always uses `default_with_last_n` (since = now − 1 day) and the wake-up tool exposes no `diary_since` parameter. Agents resuming after a long gap (weekend, incident cooldown) will silently receive truncated context with no indication that older entries were excluded.
- Unfiltered cross-wing reads are unbounded full-scans with in-memory time filtering. When `wing` is `None`, `list_drawers` retrieves all diary entries across all wings before applying the `since` predicate in `diary_entry_matches`. No server-side timestamp push-down or pagination exists; this is a performance cliff as diary volume grows.

## Analyzer Output

```text
Intent

Change the diary feature from per-agent siloed storage into shared operational memory across wings. Agent name should be treated as attribution, not the storage key. Project diary entries should be stored in the relevant project wing, while agent-specific diary entries should be stored in the shared `wing_agents` wing. Reading the diary should retrieve entries globally across wings by default so startup and agents can understand recent activity across the board.

Success Criteria

A correct implementation should make diary writes respect write scope: project-scoped entries require/use a project wing, and agent-scoped entries go to `wing_agents`. Diary entries should still record which agent wrote them.

Diary reads should default to all diary entries across all wings, filtered to the last 24 hours by default. Reads should support optional filters for `since`, `wing`, `agent_name`, and `topic`, with filters other than `since` effectively defaulting to wildcard/all. Entries returned should expose enough context to identify both the writing agent and the wing where the entry lives.
```

## Reviewer Outputs

### Claude (claude / claude-sonnet-4-6)

```text
---

**Blocking Issues**

None. The core logic — routing writes to `wing_agents` or a named project wing, filtering reads in-memory after a storage-level wing filter, attributing via `added_by` — is internally consistent and the tests cover the main paths.

---

**Non-Blocking Issues**

1. **`diary_read_all_payload` emits a redundant `"agent": null` field.** `default_with_last_n` sets `agent_name: None`, which serialises as `"agent": null` in the payload. Then `current_agent` is injected on top. The wake-up response now has both `"agent": null` and `"current_agent": "Wake Bot"` — cosmetically messy and inconsistent with what callers see from `diary_read` (where `"agent"` is the filter echo).

2. **`scope == "agent"` silently discards a provided `wing`.** The schema documents this but the Rust code raises no warning or error. A caller passing `scope: "agent", wing: "wing_some_project"` gets `wing_agents` without any indication their parameter was ignored. This is a footgun.

3. **`scope` is not persisted to drawer records.** It appears in the change event's `details_json` but not in the drawer itself. Entries written as `project`-scoped and entries written as `agent`-scoped look identical when read back (only wing provides implicit context). This creates a latent ambiguity if entries from project wings and `wing_agents` ever collide in topic/agent combinations.

4. **`last_n` is parsed outside `DiaryReadFilters::from_arguments`.** `tool_diary_read` extracts `last_n` and then passes the value into `from_arguments`, which does not re-read it from `arguments`. This split is slightly odd — either `from_arguments` should own all argument parsing, or it should not accept pre-parsed values. Minor style issue, but makes `from_arguments` surprising.

---

**Missing Tests**

1. **`scope == "project"` without a `wing` field.** The success criteria explicitly says project-scoped entries require a project wing. There is no test asserting that omitting `wing` returns `InvalidParams`. The happy path is tested; the enforcement path is not.

2. **Cross-wing unfiltered read.** No test writes one entry to a project wing and one to `wing_agents`, then issues `diary_read` with no wing/agent/topic filters and asserts both come back. The wake-up test is close but both entries go to `wing_agents` (default scope), so it doesn't exercise the multi-wing merge.

3. **Invalid `since` format.** `parse_since_timestamp` returns a user-facing error message but there is no test exercising this path.

4. **`scope == "agent"` with explicit `wing` is silently ignored.** Given this is documented as intentional, a test asserting the returned `"wing"` is `wing_agents` even when a different `wing` was passed would pin the contract.

5. **No test for wake-up with entries older than 24 hours.** `diary_read_all_payload` now applies a 24-hour `since` floor that the old `diary_read_all_agents` did not have. A test writing an entry with a fixed past `filed_at` and calling wake-up would confirm those entries are excluded — currently this truncation is untested.

---

**Strong Concerns**

1. **Wake-up diary is silently hard-capped at 24 hours with no override.** The old `diary_read_all_agents` had no time filter. The new code routes through `diary_read_payload` with `default_with_last_n`, which always sets `since = now - 1 day`. The wake-up tool has no `since` parameter, so there is no way for a caller to widen the window. In practice, if two agents hand off after a long gap (weekend, incident cooldown) the startup context will be truncated to 24 hours without any indication in the response that entries were excluded. The intent says "24 hours by default" for `diary_read`; it says nothing about baking the same window into wake-up with no escape hatch. At minimum the response should signal the time window in use, or wake-up should expose a `diary_since` parameter.

2. **Unfiltered reads are now unbounded full-scans.** When `wing` is `None`, `list_drawers` must scan the diary room across all wings. For large deployments this is a performance cliff. No pagination, no server-side `since` push-down (the time filter is applied in-memory after retrieval). This was also true of the old `diary_read_all_agents`, but the new `diary_read` inherits it too. Acceptable today, but worth flagging now before the diary grows.

---

**Confidence**

Medium-high. The implementation is coherent, the test suite covers the happy path for writes, reads, filtering, and legacy migration. The gaps are in the error-condition surface, the cross-wing unfiltered read path, and the silent 24-hour floor on wake-up. No evidence of a data-loss or data-corruption bug, but the wake-up truncation is a behavioral regression from the old unlimited history that could bite users in production without warning.
```

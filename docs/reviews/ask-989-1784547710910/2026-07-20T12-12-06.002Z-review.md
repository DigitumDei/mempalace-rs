## Executive Summary

The branch adds bounded diary summaries, returns summaries during wake-up, and supports full-content retrieval by entry ID with legacy truncation fallback. The core implementation meets the intended behavior, but diary content and summaries are persisted independently across Lance and SQLite, so failures can leave durable entries without their authored summaries while reporting an error. This unresolved cross-store consistency defect is blocking, so the branch requires revision.

## Blocking Issues

- Diary entry and summary persistence are not atomic or reconciled (lib.rs): The diary drawer is committed to Lance before its summary is stored in SQLite. If summary persistence fails or the process crashes between operations, a durable entry remains without its supplied summary; wake-up silently derives a different truncated fallback, and retries can create duplicates.

## Non-Blocking Issues

- Entry-ID reads remain affected by pagination and conflicting filters (lib.rs): When entry_id is supplied, since and last_n can suppress a matching entry, so direct retrieval semantics are not fully reliable.
- Wake-up performs one summary query per diary entry (lib.rs): Summary lookup uses an N+1 query pattern, creating unnecessary SQLite connection and query overhead as wake-up history grows.
- Summary length is enforced only by the MCP handler (sqlite.rs): DiaryStore and the SQLite schema accept summaries longer than 400 characters, so callers bypassing the handler can violate the persisted-summary invariant.
- Diary deletion leaves orphaned summary rows (lib.rs): Deleting a diary drawer does not remove its corresponding SQLite summary, allowing permanent orphan records to accumulate.
- Checked-in MCP contract fixture is incomplete (tests/fixtures/phase0/goldens/mcp-contract.json): The fixture is partially updated but omits the live diary_write summary field and diary_read entry_id field, so it no longer fully represents the protocol.
- Entry-ID reads expose an internal epoch timestamp (lib.rs): The response reports since as UNIX_EPOCH when the caller did not provide a since boundary, which is misleading for direct entry retrieval.

## Missing Tests

- Failure and crash-path behavior when drawer persistence succeeds but summary persistence fails.
- Entry-ID reads with conflicting since and last_n values.
- Exact 400-character summaries, including multibyte Unicode.
- Summary persistence across restart and migration from an existing database.
- Cleanup of summary rows when diary entries are deleted.
- Empty-summary behavior.

## Disputed Issues

- Whether all filters such as agent_name, topic, and wing should be ignored when entry_id is supplied, or whether they are legitimate narrowing filters.
- Whether empty summaries must be rejected, since the current requirements do not explicitly define a minimum length.
- Whether missing-summary fallback provenance requires a new response field or is acceptable as legacy compatibility behavior.

## Outstanding Concerns

- The fallback truncation can silently mask failed summary writes and is indistinguishable from an authored summary.
- The change log is also best-effort and is not coordinated with drawer or summary persistence.

Let me now look at the `tool_diary_read` path when `entry_id` is provided, and check how `diary_read_payload` handles it.
**Blocking Issues**

1. **Summary storage is not atomic with drawer commit.** In `tool_diary_write` (lib.rs:1400–1414), the drawer is committed first via `commit_ingest`, then `store_diary_summary` is called separately. If `store_diary_summary` fails (or the process crashes between the two calls), the drawer exists in Lance but has no summary row. The `legacy_diary_summary` fallback in `wake_up_diary_payload` (lib.rs:1520–1522) silently masks this by truncating the content to 400 characters. The user-provided summary is lost with no indication. Either wrap both operations in a transaction, or store the summary before the commit and roll back the drawer if the summary write fails.

**Non-Blocking Issues**

1. **N+1 SQL queries in wake-up.** `wake_up_diary_payload` (lib.rs:1516–1522) calls `get_diary_summary` once per entry. For a 12-entry wake-up that's 12 round-trips to SQLite. A batch query (`SELECT entry_id, summary FROM diary_summaries WHERE entry_id IN (...)` ) would be more efficient.

2. **`diary_read` response `since` field leaks `UNIX_EPOCH` when `entry_id` is provided.** `DiaryReadFilters::from_arguments` (lib.rs:2370–2371) defaults `since` to `UNIX_EPOCH` when `entry_id` is set, but `diary_read_payload` (lib.rs:1483) always emits `"since"` in the response. This produces `"since": "1970-01-01T00:00:00Z"` for entry-ID lookups, which is semantically misleading. Omit the field or use the entry's actual timestamp when `entry_id` is set.

3. **Breaking change: `summary` is now required in `diary_write`.** The updated tool schema (lib.rs:442) adds `"summary"` to the `required` array. All internal callers are updated, but any external client or script that calls `diary_write` without `summary` will get an `-32602` error. No backward-compatible path (e.g., deriving a summary from the entry if missing) is provided.

4. **Empty summary string passes validation.** `validate_diary_summary` (lib.rs:2440–2448) only checks `max` length. An empty string (`""`) passes the `≤ 400` check. The protocol description says "a concise summary," but the implementation doesn't enforce a minimum. Consider rejecting empty strings.

5. **`diary_entry_matches` applies `since` filter before `entry_id` filter.** (lib.rs:2387–2398) If a caller passes both `entry_id` and a `since` timestamp that postdates the entry, the entry won't be found even though the `entry_id` matches. The `since` check should be skipped when `entry_id` is provided.

**Missing Tests**

1. `diary_read` with `entry_id` for a non-existent entry — should return empty entries with appropriate message.
2. `diary_write` with summary of exactly 400 characters (boundary validation).
3. `diary_write` with empty summary string — behavior is unspecified.
4. `diary_read` without `entry_id` still returns `content` field (not `summary`) — no test asserts this existing contract is preserved.
5. `diary_read` with `entry_id` + contradictory `since` filter — entry should still be found.
6. Error path: `store_diary_summary` failing after successful drawer commit — the lost-summary scenario.

**Strong Concerns**

1. **Silent fallback on missing summary.** When a summary row is absent (legacy entries, failed writes, deleted rows), `wake_up_diary_payload` (lib.rs:1522) calls `legacy_diary_summary`, which truncates full content to 400 characters. The caller cannot distinguish a real summary from a truncated-content fallback. For long entries, this can produce broken mid-sentence "summaries." Consider adding a field like `"summary_source": "explicit" | "legacy_truncation"` or returning `null` for summary when none exists.

2. **No backfill migration for existing entries.** The `0006_diary_summaries` migration creates the table but doesn't populate it. All pre-existing entries forever rely on the `legacy_diary_summary` truncation fallback. This is acceptable per the success criteria ("Gracefully support legacy entries"), but the quality of the fallback summaries is uncontrolled.

**Confidence:** Medium-High. The core logic is correct — summaries are bounded, wake-up returns summaries (not content), `diary_read` with `entry_id` returns full content. The main risk is the non-atomic summary storage and the silent fallback masking real failures.
